# 실험파 — 정상 순서를 뒤집는 제품 회귀 조건 3개

2026-10-13. 범위: TourSafe 전체 흐름을 대상으로 빈 결과의 연속 조작, 독립 데이터 도착 순서, 비동기 갱신 중 키보드 조작을 검토했다. 초록 지도·전국 시설·도움·여행지·저장이라는 제품 구성은 유지한다. 이전 두 전략의 발견이나 다른 도전자 보고서는 사용하지 않았다.

**판정:** 기존 함수별 정상/오류 검증에 더해, 사용자가 작업하는 도중 다른 상태가 바뀌는 조건을 세 개 추가하는 것이 효율적이다. 아래 세 조건은 API 키나 실서버에 의존하지 않도록 재현할 수 있다.

이번 실행은 코드 읽기와 메모리 안의 작은 Node 실험뿐이다. 앱 코드를 수정하지 않았고, 브라우저를 조작하지 않았으며, 외부 API 호출도 하지 않았다. 기존 127개 테스트라는 수치는 제공받은 기준이고 이번에 재실행하여 새로 센 숫자가 아니다. 현재 테스트 파일에서 이 세 가지 제품 흐름을 검증하는 항목은 찾지 못했다. `tests/map-layers.test.ts`는 군집 배열·간격·병합을 검증하고 `tests/tour-live.test.ts`는 공급자 데이터 처리 등을 검증하지만, 실제 클릭 후 요청 횟수나 DOM 포커스를 검증하지 않는다.

## 실험 1. 처음부터 10km를 고른 뒤 빈 결과의 ‘다시 찾기’를 누른다

**가설:** 새로운 options 객체를 만들기 때문에 재조회될 것이다.

**확인 사실:** 빈 결과 버튼은 `frontend/src/ExploreApp.tsx:480`에서 반경을 10000으로 만들고 `:481`에서 `{ ...options, radius: 10000 }`을 적용한다. 버튼 이름은 `:490`의 ‘10km로 다시 찾기’다. `frontend/src/hooks/useRecommendations.ts:35`의 effect는 객체 자체가 아니라 `lat/lng/radius/withKids/retry`의 값이 바뀔 때만 실행한다. 따라서 이미 10km인 상태에서는 새 객체를 만들어도 조회 의존값이 바뀌지 않는다. 일반 검색 함수는 같은 조건이면 `refresh()`하는 방어가 있으나(`ExploreApp.tsx:100`–`:107`), 이 빈 결과 버튼에는 없다.

**작게 실행한 반증:** 현재 handler와 동일하게 반경 10000 객체를 다시 만들고 effect 의존값을 `Object.is`로 비교했다. 출력은 `{ newObject: true, effectDependenciesChanged: false }`였다. 이는 React UI 클릭을 실측한 결과가 아니라, 조회를 결정하는 값의 동등성을 확인한 실험이다.

**브라우저 재현 조건 — 미실행:** LIVE 추천 응답을 빈 배열로 고정 → 반경 10km로 검색 → ‘10km로 다시 찾기’ 클릭. 서버 요청 횟수가 증가하는지 기록한다. 현재 코드에서는 증가하지 않을 것으로 판단한다. ‘전체’ 필터와 LIVE 상태에서 시험해야 다른 빈 결과 분기를 타지 않는다.

**영향:** 반복해서 눌러도 아무 변화가 없는 복구 버튼이 된다. 첫 번째 3km→10km 전환만 시험하면 놓칠 수 있다. 심각도 P2.

**최소 개선:** 이미 10km면 `refresh()`를 실행하거나 버튼을 `다른 위치 선택`으로 바꿔 실제 복구 경로에 연결한다. 10km 미만이면 지금처럼 반경을 넓힌다. 반복 호출을 무작정 추가하는 것보다 빈 결과 이유와 다음 행동을 맞추는 편이 낫다.

**추가할 회귀 검증:** 같은 fixture로 3km 빈 결과→10km는 한 번 재조회되고, 이미 10km에서 누르면 한 번 재조회되거나 실제 위치 선택 화면이 열린다. 새 객체가 생성됐다는 내부 사실을 검사하지 말고 요청/화면 행동을 검사한다.

## 실험 2. 시설 3종은 즉시 성공시키고 날씨만 마지막에 완료한다

**가설:** 경찰·의료·공공시설이 준비됐으면 지도 시설을 먼저 사용할 수 있을 것이다.

**확인 사실:** `backend/src/services/mapFacilities.ts:14`는 `local/medical/police/weather` 네 결과를 하나의 `Promise.all`로 기다린다. 날씨도 `:21`에서 같은 집합에 포함되며 전체 응답은 `:37`에 이르러야 반환된다. `backend/src/adapters/weatherApi.ts:36`의 실황 조회 뒤에 `:81`의 예보 조회가 이어지고, 실제 지도 설정의 날씨 카드(`frontend/src/components/LivePlacesMap.tsx:124`)는 기온·상태만 보여준다. 예보까지 기다리는 동안 이미 준비된 경찰·화장실 자료도 반환되지 않는다. 개별 외부 요청 시간제한은 `backend/src/utils/http.ts:36`의 9000ms다. 실제 사용자 지연시간을 측정한 것은 아니다.

**작게 실행한 반증:** 공공시설·의료·경찰을 이미 완료된 Promise로, 날씨만 수동 해제할 Promise로 두고 현재와 같은 집계 방식을 실행했다. 날씨가 미완료일 때 `responseComplete: false`, 날씨 해제 뒤 `responseComplete: true`였다. 네트워크 속도나 실 API 성능을 측정한 결과가 아니라 응답 의존관계를 확인한 것이다.

**통합 재현 조건 — 미실행:** 시설 fixture는 즉시 성공, 날씨 fixture는 제어 가능한 대기 상태로 둔다. 지도 시설 목록과 전화/길찾기를 날씨 해제 전에 사용할 수 있는지 확인한다. 날씨 응답만 실패시키는 시험보다, 실패가 확정되기 전 오랫동안 대기하는 시험이 핵심이다.

**영향:** 도움 시설의 준비 속도가 현재 화면에 보이지도 않는 날씨 조회에 묶인다. 연결이 나쁜 환경에서 사용자는 시설 자체가 느리다고 받아들일 수 있다. 심각도 P2. 도움 화면의 112·119는 별도 경로이므로 긴급전화 버튼도 이 지연에 묶인다고 주장하지 않는다.

**최소 개선:** 지도 시설 응답과 지도 날씨를 분리하고 날씨는 설정을 열 때 조회하거나 독립적으로 갱신한다. 응답 호환성상 즉시 분리하기 어렵다면 시설을 먼저 반환하면서 날씨를 별도 상태로 처리할 계약을 마련한다. 날씨가 없다고 시설을 ‘없음’으로 표시하면 안 된다. 색·군집·시설 데이터는 바꿀 필요가 없다.

**추가할 회귀 검증:** 완료 순서를 `[시설→날씨]`, `[날씨→시설]`, `[시설→날씨 실패]`로 바꿔도 시설 목록·전화·길찾기 준비 상태는 같은 시점에 가능해야 한다. 실제 시간을 sleep으로 재지 말고 deferred Promise 해제 전후를 검사한다.

## 실험 3. 경찰 핀에 키보드 포커스를 둔 채 병원 데이터가 늦게 도착한다

**가설:** 이미 표시된 경찰 핀은 그대로 남고 새 병원 핀만 추가될 것이다.

**확인 사실:** `frontend/src/components/TourSafeMapPanel.tsx:113`–`:114`의 `drawMarkers`는 기존 모든 마커를 제거한다. 이후 `:119`에서 각 button을 다시 만들며 `:147`에서 새 마커를 추가한다. 이 함수는 지도 이동 완료(`:151`)와 resize(`:152`)에 연결되고, effect 자체도 `points` 변경 때 정리·재생성한다(`:154`–`:155`). 이 경로에는 포커스를 보관·복원하는 처리가 없다. 한편 전체 points는 시설과 별도 병원 조회 결과를 합쳐 생성하므로(`frontend/src/components/LivePlacesMap.tsx:83`–`:91`) 다른 데이터의 늦은 도착이 기존 핀도 다시 만들 수 있다.

**검증 수준:** DOM 노드를 모두 제거한다는 사실은 코드로 확정했다. 그 순간 브라우저·보조기기에서 포커스가 어디로 이동하고 다음 Tab이 어디서 시작하는지는 이번에 실행하지 않았다. 따라서 ‘접근성 실패를 실측했다’는 결론은 내리지 않는다.

**브라우저 재현 조건 — 미실행:** 경찰 응답은 먼저, 병원 응답은 대기 → Tab으로 특정 경찰 핀에 포커스 → 병원 응답 해제 → 동일 경찰 핀에 포커스가 남는지와 Enter로 그 시설을 선택하는지 확인한다. 별도 변형으로 포커스를 둔 상태에서 viewport resize를 한 번 발생시킨다. 마우스 클릭만 시험하면 드러나지 않을 수 있다.

**영향/추정:** 스크린리더·키보드 사용자가 시설을 찾던 중 작업 위치를 잃고 처음부터 다시 탐색할 가능성이 있다. 마커 개수와 좌표만 맞는 테스트는 이를 보장하지 못한다. 심각도는 실기 재현 시 P2로 제안한다.

**최소 개선:** 안정적인 ID로 마커를 재사용한다. 우선 작은 수정으로는 실제 포커스가 마커에 있을 때만 해당 시설 ID를 기록하고 재생성된 대응 핀으로 복원한다. 군집이 달라졌다면 같은 시설을 포함하는 군집으로 연결한다. 사라진 시설이면 주변 목록 버튼 등 명확한 복귀점을 제공한다. 비동기 응답 때 다른 입력창에서 작업하는 사용자에게 포커스를 빼앗으면 안 된다.

**추가할 회귀 검증:** 기존 시설 포커스 보존, 해당 시설 제거 시 명시적 복귀, 입력창 편집 중 배경 데이터 도착 시 포커스 비탈취를 한 fixture에서 확인한다. DOM이 필요한 이 한 조건만 브라우저 테스트로 두면 된다.

## 실행 제안과 반증 기준

우선순위는 **빈 결과 복구 버튼의 실제 동작 → 시설과 날씨의 응답 분리 → 비동기 마커 갱신 중 포커스 유지**다. 앞의 두 조건은 통제된 응답과 상태 관찰로 저렴하게 검증하고 마지막 하나만 실제 브라우저에 맡긴다. 수십 가지 화면 캡처를 추가하는 방식보다, 각 조건에서 이용자가 하려던 다음 행동이 유지되는지 한 번씩 검사한다.

이번 보고서에서 초록 지도를 없애거나 전국 시설을 축소할 이유는 발견하지 못했다. 기존 단위 테스트 통과와 별개로 이 세 조건을 통과해야 ‘빈 결과에서도 복구되고, 일부 자료가 늦어도 도움을 찾고, 작업 중 갱신되어도 조작을 이어갈 수 있다’는 사용자 계약을 확인할 수 있다. 실패율·재현 횟수·브라우저 실측 수치는 만들지 않았다.
