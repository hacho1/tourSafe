# 정석파 전체 점검안 — 2026-10-13

**판정: 기능 단위 구현은 상당히 갖춰졌으나, 위치·저장·도움의 화면 간 계약을 먼저 정리해야 한다.** 초록색 커스텀 지도, 숫자 군집을 누르면 확대하고 같은 좌표는 목록으로 여는 방식은 유지한다. 우선순위는 지도 교체나 기능 증설보다 `어느 위치를 보는가 → 무엇을 찾는가 → 다음 행동 → 실패 시 복구`의 연속성이다.

검토 범위는 지도, 위치 선택, 시설 목록, 병원 연동 상태, 도움/흔들기, 여행지 검색·상세, 저장, 공통 모달이다. 앱 코드·설정·데이터는 수정하지 않았다. 독립적인 브라우저 실행은 하지 않았다. 아래에서 **코드 확인**, **함수 실행 확인**, **부모 브라우저 확인**, **사용성 추정**을 구별한다. 전국 화장실 53,584건/46,945건 좌표 연결은 제공된 작업 맥락이며 이번 점검에서 다시 집계하지 않았다.

## 확인한 문제 4건

### 1. 지도에서 선택한 위치가 여행지 찾기로 이어지지 않는다 — P2, 최우선

- **사실/근거:** 지도는 `frontend/src/pages/SafetyMap.tsx:15`에서 자체 `location`을 소유한다. 여행지는 `frontend/src/ExploreApp.tsx:42`와 `:46`에서 `DEFAULT_REGION`으로 별도 초기화한다. `frontend/src/App.tsx:68`, `:71`은 위치를 전달하지 않고 페이지 이동 함수만 전달한다.
- **재현:** 처음 접속 → 지도 조회 위치를 안성·부산 등 성수 밖으로 변경 → 여행지 탭 → 여행지 출발 위치와 첫 조회가 서울 성수가 된다. 부모가 **한경국립대학교 안성캠퍼스 → 여행지 탭 → 서울 성수**를 브라우저에서 실제 확인했다고 전달했다. 이미 여행지를 방문했다면 그 화면의 이전 검색 위치가 남는 구조다.
- **영향:** 같은 앱에서 계속 주변을 탐색한다고 생각한 사용자가 전혀 다른 지역 결과를 받는다. 위치가 표시되기는 하므로 “위치를 숨긴다”는 지적은 아니며, 탭 이동 시 연속성이 깨지는 문제다.
- **최소 수정:** `App`으로 조회 위치를 올리고 지도에서 여행지로 이동할 때 그 위치를 여행지 검색의 초기/적용 위치로 전달한다. 여행지에서 독립적인 계획 위치를 유지하려면 `지도 위치로 찾기`를 명확히 표시하고 두 기준을 구별한다. 자동 공유 정책이 제품 목적에 더 일관적이다.
- **완료 기준:** 비서울 지도 위치 → 여행지 → 지도 왕복 시 사용자가 바꾸지 않은 기준 위치가 바뀌지 않는다. GPS 위치와 여행 계획 위치를 의도적으로 분리할 경우 그 차이가 각 화면 첫 화면에서 읽힌다.

### 2. 저장 목록은 저장한 장소 전체를 다시 여는 목록이 아니다 — P2

- **사실/근거:** `frontend/src/utils/savedPlaces.ts:10`은 ID만 보관하고 `:36`도 이를 명시한다. `frontend/src/ExploreApp.tsx:68`–`:74`는 **현재 추천 결과와 저장 ID의 교집합**만 보여준다. 원본 관광 후보는 `backend/src/adapters/tourApi.ts:97`–`:99`에서 가까운 8개로 제한된다. 이전 검색은 `ExploreApp.tsx:57`의 메모리 ref 하나뿐이며 새로고침하면 없어진다. 범위 안내(`:359`–`:362`)는 정직하지만 재열기 경로는 제공하지 않는다.
- **재현:** 부산 여행지를 저장 → 다른 지역 검색 또는 새로고침 → 저장 탭. 총 저장 수는 남아도 현재 추천 8개에 없는 장소의 이름·주소·상세·저장 해제 버튼은 나타나지 않는다. 지도에서 성수 밖 여행지를 저장하고 처음 저장 탭을 여는 경우에도 동일 구조다. 이는 코드로 확인한 재현 절차이며 이번 에이전트의 브라우저 실행 결과는 아니다.
- **영향:** 여행 전에 저장해 둔 곳을 현장에서 찾기 어렵다. “남아 있다”는 안내를 읽어도 사용자가 어느 지역에서 저장했는지 기억해서 검색을 복원해야 한다. 같은 반경에 들어 있어도 가까운 8개 밖이면 표시되지 않을 수 있다.
- **최소 수정:** 저장 레코드에 `id/name/address/lat/lng/savedAt` 최소 정보를 보관하고 저장 탭은 그 레코드를 직접 그린다. 상세를 열 때 최신 정보를 재조회하고, 실패하면 저장 당시 이름·주소와 길찾기·삭제는 남긴다. 과거 ID 전용 레코드는 별도 상세 조회로 보완한다. 저장 당시 운영정보를 현재 정보처럼 보여주지 않는다.
- **완료 기준:** 서로 다른 지역 2곳 저장 → 새로고침 → 저장 탭에서 둘 다 확인·길찾기·삭제 가능. 현재 추천 조회가 실패해도 저장한 이름과 주소는 접근 가능하다.

### 3. 흔들기 ‘켜짐’이어도 모든 모달에서 감지가 중단된다 — P2

- **사실/근거:** `frontend/src/hooks/useShake.ts:25`는 열린 `dialog`가 하나라도 있으면 샘플을 초기화하고 반환한다. `:33`도 모든 dialog를 비활성 조건으로 쓴다. 반면 `frontend/src/components/EmergencyHelp.tsx:116`은 “앱 화면을 보고 있을 때, 흔들면 이 화면을 열어요”라고 설명하고 `enabled`만으로 켜짐을 표시한다. `frontend/src/App.tsx:34`가 넘기는 명시적 pause는 도움 화면이 열린 상태뿐이어서, 추가적인 전체 모달 차단은 훅 내부에 숨어 있다.
- **재현:** 지원 기기에서 흔들기 활성화 → 도움 닫기 → 주변 시설 목록, 위치 선택, 병원 시간표 또는 여행지 상세 열기 → 흔들기. 코드상 감지 함수 호출 전에 반환한다. 지원 기기 센서 실측은 수행하지 않았다.
- **영향:** 이용자가 시설·병원 정보를 읽는 도중에도 앱을 보고 있지만 약속된 단축 행동이 작동하지 않는다. 각 모달의 도움 버튼은 있으므로 긴급 연락 경로 전체가 사라진다는 주장은 하지 않는다.
- **최소 수정:** 도움 모달이 열렸거나 앱이 숨겨졌을 때만 재진입을 막고, 일반 모달 위에서는 도움을 열 수 있게 한다. 기존 버튼으로 열 때처럼 닫으면 원래 모달·포커스로 복귀한다. 모든 모달 차단이 의도된 정책이라면 설명과 상태를 ‘목록·상세 창에서는 잠시 멈춤’까지 정확히 바꾸되, 긴급 단축 기능으로서는 전자가 낫다.
- **완료 기준:** 지도/시설 목록/병원/여행지 상세에서 같은 센서 입력으로 도움을 한 번만 연다. 도움 자체에서는 재진입하지 않고 닫을 때 원래 작업 위치로 복귀한다.

### 4. 조회 반경보다 훨씬 큰 위치 오차도 별도 처리 없이 ‘내 위치’ 조회에 사용한다 — P2

- **사실/근거:** `frontend/src/utils/searchLocation.ts:19`는 정확도가 유한한 0 이상의 값인지만 검사한다. `:25`–`:35`는 정확도와 시각을 `address` 문자열로 바꾸며 구조화된 값을 보존하지 않는다. `frontend/src/utils/helpLocation.ts:2`의 지도 위치 모델에도 정확도 필드가 없다. 지도는 `frontend/src/components/LivePlacesMap.tsx:81`에서 3km 검색을 실행하고 `:123`에서 점 표식의 이름을 ‘확인한 내 위치’로 쓴다. **정확도 자체는 `:131`에 표시되므로 정확도를 숨겼다는 문제는 아니다.**
- **함수 실행 확인:** 현재 시각, 성수 좌표, `accuracy: 25000`인 가상 읽기를 `isFreshSearchLocation`에 전달한 결과 `accepted: true`; `searchLocationRegion` 결과는 `정확도 약 25000m` 주소 문자열과 동일 좌표였다. 기기에서 실제 25km 오차가 나왔다고 주장하지 않는다.
- **재현 명령:** `node --import tsx --input-type=module -e 'import { isFreshSearchLocation, searchLocationRegion } from "./frontend/src/utils/searchLocation.ts"; const now = Date.now(); const reading = { latitude: 37.5445, longitude: 127.0374, accuracy: 25000, timestamp: now }; console.log({accepted: isFreshSearchLocation(reading, now), result: searchLocationRegion(reading)});'`
- **영향/추정:** 오차가 조회 반경보다 클 때 ‘직선 300m’ 같은 시설 거리가 이용자의 실제 위치와 크게 다를 수 있다. 작은 정확도 문구를 읽지 않으면 지도 점이 과도하게 확정적으로 느껴질 가능성이 있다. 인지 영향은 사용성 추정이다.
- **최소 수정:** `accuracyMeters/capturedAt`을 구조화해 보존한다. 정확도와 조회 반경을 비교하여 큰 오차에는 `위치가 대략적이에요` 상태와 `다시 확인`·`장소 직접 선택`을 바로 제공한다. 추정 위치를 계속 쓸 선택지도 유지하되 기준이 대략적임을 시설 거리 옆에 연결한다. 자동 추적은 필요 없다.
- **완료 기준:** 정밀/중간/반경 초과 가상 측정값을 넣었을 때 상태가 구분된다. 큰 오차에서 시설이 없다는 결론을 유도하지 않고 수동 선택으로 곧바로 복구할 수 있다.

## 정성 제안 2건 — 결함 확정과 구분

1. **숫자 군집은 유지하되 ‘필요한 도움’을 먼저 찾게 한다.** `frontend/src/components/TourSafeMapPanel.tsx:125`–`:131`에서 혼합 군집의 시설 종류는 접근성 이름에는 있지만 시각 표식에는 숫자만 남는다. 기본 CCTV/경찰/의료 동시 표시(`frontend/src/utils/mapLayers.ts:8`)는 밀집 지역에서 경찰·병원의 존재를 즉시 읽기 어렵게 만들 수 있다. 초록 지도·숫자 원을 유지하면서 `경찰 찾기/병원 찾기/화장실 찾기`를 누르면 해당 종류를 우선 강조하고 근처 목록 3개를 보여주는 행동 중심 진입을 제안한다. 숫자 원에 작은 종류 힌트를 붙이는 안과 비교한다. 실제 찾는 시간 개선은 360px 모바일 과업 테스트로 판정해야 한다.

2. **긴급 도움 버튼의 의미를 첫눈에 알게 하고, 지도 실패와 독립시킨다.** 현재 모바일 탭의 이름은 ‘도움’이고 도움 화면 안에서는 112/119가 명확하다. 첫 화면 버튼에 짧은 ‘112·119’ 보조 표기 또는 ‘긴급 도움’ 이름을 검토한다. 앱에는 지도 동적 import와 `Suspense`가 있으나 오류 경계가 보이지 않는 구조(`LivePlacesMap.tsx:16`, `:122`; `main.tsx:5`)이므로, 지도 청크 실패를 주입하여 도움 버튼과 시설 목록이 남는지 검증하고 필요한 경우 지도 부분에 오류 경계를 둔다. 이것은 이번 브라우저에서 백지 화면을 관찰했다는 뜻이 아니다.

## 유지할 강점과 실행 순서

전화는 위치 확인 없이 즉시 선택할 수 있고(`EmergencyHelp.tsx:85`–`:94`), 지도 위치와 긴급 전달 위치는 섞지 않는다(`:124`). 화장실 주소 좌표 주의문, CCTV 설치자료 한계, 부분 조회 범위, 병원 전화 확인 문구는 유지한다. 숫자 군집은 같은 좌표의 선택 불가능 문제를 다루는 올바른 방향이다.

먼저 공통 위치와 저장 데이터 계약을 고친다. 이어 흔들기 동작 범위와 부정확한 위치 상태를 맞춘다. 그 뒤 **비서울 위치 → 주변 도움 → 여행지 → 저장 → 재접속**, **일반 모달 → 흔들기 → 도움 → 복귀**, **큰 위치 오차/권한 거부/지도 실패 → 복구**의 짧은 종단 흐름으로 확인한다. 시각 변경은 이 계약을 해치지 않는 범위에서 초록 지도 위에 적용한다.
