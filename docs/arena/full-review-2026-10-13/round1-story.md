# 1라운드 · 스토리파 — 밤 10시, 낯선 숙소 앞에서 다음 행동을 찾는 사람

가상 점검 장면이다. 여행자 민서는 낮에 여행지를 둘러보고 저장한 뒤, 밤에 낯선 숙소 앞에서 몸이 불편해 병원에 먼저 전화하려고 한다. 위치 권한은 허용하지 않았고, 주변 지명도 익숙하지 않다. 특정 증상에 대한 의료 판단을 하는 장면은 아니며, 긴급 상황이라면 도움 화면에서 즉시 연락할 수 있어야 한다.

2026-10-13 `D:/tourSafe`의 실제 코드 경로를 읽어 이 흐름을 점검했다. 브라우저·전화·센서·외부 API 실험은 하지 않았다. 아래는 소스로 확정 가능한 동작과, 그 동작이 이 여행자에게 줄 수 있는 부담을 구분한 결과다. 초록색 커스텀 지도와 전국 시설 자료를 유지하는 범위에서 제안한다.

## 장면 1 · 시작 — 내 위치를 못 받았으니 숙소 이름을 검색한다

**P2 · 위치 복구 흐름의 긴 대기에 명시적인 탈출 행동이 부족하다.**

확인한 사실: 지도 위치 요청은 11초 watchdog을 두며, 거절되면 직접 검색을 안내한다. 위치 선택 창의 장소 검색은 공통 API 함수의 90초 timeout을 그대로 사용한다. 대기 중에는 검색 버튼이 비활성화되고 `장소를 찾고 있어요…`가 나온다. 검색어를 바꾸거나 창을 닫으면 요청이 취소되지만, 화면에 `검색 취소`나 `지도에서 위치 고르기`라는 행동은 없다. 연결 실패 시 안내는 다시 검색 또는 준비된 시작 위치 선택이다. 사용자가 90초를 반드시 기다린다는 뜻은 아니며, 지연된 연결에서 허용하는 상한과 표시 구조를 확인한 것이다.

근거: `frontend/src/utils/searchLocation.ts:69`, `:85`; `frontend/src/components/HelpLocationPicker.tsx:14`, `:16`, `:22`, `:27`, `:29`, `:38`, `:40`, `:43`; `frontend/src/services/api.ts:9`, `:28`.

재현 절차(미실행): 위치 권한을 거절한다 → 숙소 이름 검색 창을 연다 → 장소 검색 응답만 지연시킨다 → 대기 문구와 비활성화된 검색 버튼 외에 취소·수동 위치 선택이 명확히 노출되는지 확인한다. 닫기 또는 검색어 변경으로 취소할 수 있다는 사실도 함께 확인해야 한다.

영향 추정: 민서는 이름을 틀렸는지, 기다려야 하는지, 나가면 작업을 잃는지 판단해야 한다. 밤에 도움이 필요한 상황에서 복구 방법이 숨은 조작에 의존한다.

최소 개선: 검색 대기 중 `검색 취소`를 제공하고, 실패 메시지 옆에 `지도에서 위치 고르기`를 둔다. 장소 검색에는 긴 추천 조회와 구분된 대기 정책을 적용한다. 시작 위치 프리셋은 그대로 두되 “내 주변 도움”으로 오해하지 않게 현재와 같은 이름·주소 표기를 유지한다.

## 장면 2 · 장소 판단 — 병원 이름과 전화번호를 받았는데 상세가 실패한다

**P2 · 진료시간을 못 읽었다는 이유로 이미 확보한 연락처까지 버린다.**

확인한 사실: 병원 기본 목록 정규화에는 이름·좌표·주소·전화번호가 들어간다. 상세 조회 실패 시에는 원래 병원 객체를 보존하고 `detailStatus: ERROR`를 붙인다. 그런데 후보 전체의 상세 조회가 실패하면 서비스가 `ALL_HOSPITAL_DETAILS_FAILED`를 던져 그 목록 전체를 응답하지 않는다. 프런트엔드는 병원 오류 화면과 `다시 조회`를 표시한다. 일부 상세만 실패한 경우에는 전화 확인 가능한 카드를 유지하므로, 실패 비율이 100%가 되는 순간 연락 가능한 기본 정보도 사라진다.

근거: `backend/src/adapters/hospitalApi.ts:63`, `:65`, `:66`; `backend/src/services/hospitals.ts:62`, `:65`, `:70`; `frontend/src/components/HospitalFinder.tsx:136`, `:139`, `:200`, `:204`. `tests/hospitals.test.ts:187`은 이 전체 실패 예외를 기대하는 기존 테스트 근거이며 이번 점검에서는 실행하지 않았다.

재현 절차(미실행): 기본 목록 API는 유효한 병원 한 곳과 전화번호를 돌려주고, 그 병원의 상세 API만 실패하도록 테스트 더블을 구성한다 → 서비스가 기본 목록을 반환하지 않고 예외를 던지는지 확인한다 → 화면에서 이미 받은 전화번호를 쓸 수 없는지 확인한다. 실제 운영 API 장애를 관찰했다는 주장은 아니다.

영향 추정: 민서에게 당장 필요한 것은 “지금 접수 가능한지 물어볼 전화번호”일 수 있다. 시간표 확인 실패가 전화 문의까지 막으면서 같은 실패한 조회를 반복하게 만든다.

최소 개선: 목록 자체가 검증됐다면 모든 상세가 실패해도 기본 카드와 연락처를 유지한다. 각 카드에 `진료과·시간표를 확인하지 못했어요. 전화로 확인해 주세요`를 명확히 표시하고 상세 재조회만 별도로 제공한다. 기본 목록까지 실패했을 때와 구분한다.

## 장면 3 · 다른 후보 — 구 경계 바로 건너편 병원이 검색 대상 밖이다

**P2 · 빈 결과를 정직하게 설명하지만, 그 다음 선택이 이어지지 않는다.**

확인한 사실: 좌표 기반 병원 검색은 해당 좌표의 행정구역을 먼저 구하고 그 시군구 목록만 요청한 뒤 5km로 제한한다. 인접 시군구는 포함하지 않는다고 UI에 알린다. `origin`이 있는 병원 화면에서는 지역 선택기가 숨겨진다. 결과가 0건인 실자료 상태는 `실제로 이 지역에 병원이 없다는 뜻은 아니에요`를 표시하지만, 그 빈 상태 안에는 기준 위치 변경·인접 지역 조회·다른 검색 경로 버튼이 없다. 헤더의 도움과 닫기, 목록 새로고침은 여전히 가능하다.

근거: `backend/src/services/hospitals.ts:50`, `:52`, `:75`; `backend/src/adapters/hospitalApi.ts:103`; `frontend/src/components/HospitalFinder.tsx:101`의 `!origin` 지역 선택 분기, `:146`, `:154`, `:157`, `:163`.

재현 절차(미실행): 행정구역 A의 경계 부근을 조회 위치로 정한다 → A 조회 목록은 비어 있고 가까운 B 지역에는 후보가 있는 조건을 만든다 → 요청에 A만 포함되는지, 빈 화면에서 바로 B나 다른 기준 위치로 전환할 수 있는지 확인한다. 특정 실제 지역에 병원이 누락되었다고 확인한 것은 아니다.

영향 추정: 민서는 앱 설명을 믿어 “없다는 뜻은 아니다”까지는 알지만, 어디로 가서 다시 찾아야 할지 결정할 수 없다. 같은 기준으로 재조회해도 행정구역 경계는 바뀌지 않는다.

최소 개선: 빈 결과 안에 `조회 위치 바꾸기`를 붙이고, 시군구 제한을 포함한 한 문장으로 다음 행동을 안내한다. 가능하면 인접 지역까지 확장하되, 현재 범위를 임의로 전체 병원 검색이라고 부르지 않는다. 긴급 도움 버튼은 계속 노출한다.

## 장면 4 · 연락과 복귀 — 지도 조회가 안 돼도 연락은 계속할 수 있어야 한다

여기서는 이미 좋은 경로가 있다. 일반 대화창 헤더에서 도움을 열 수 있고(`frontend/src/components/Modal.tsx:57`), 도움 화면의 112·119 전화 링크는 위치 확인 없이 사용할 수 있다(`frontend/src/components/EmergencyHelp.tsx:89`, `:90`). 번호를 직접 입력하는 대안도 있다(`:93`). 따라서 위 실패 상태는 연락 버튼까지 막아서는 안 된다.

위치를 전해야 한다면 `내 위치 확인·전달`을 펼치고, GPS를 허용하지 않은 민서는 그 안의 `주소·건물 이름 직접 적기`를 다시 펼쳐야 한다(`EmergencyHelp.tsx:96`, `:107`). 이를 새 결함으로 단정하지 않지만, 위치 실패 뒤에는 이 입력을 자동으로 펼치는 편이 장면과 맞는다. 지도에서 고른 숙소를 현재 위치로 자동 전송해서는 안 되며, 본인이 주변 표지를 확인해 적게 한다.

닫기 복귀는 `App.tsx:35`에서 원래 트리거에 초점을 돌려준다. 또한 도움 화면 입력은 닫으면 지워지는 정책을 안내한다(`EmergencyHelp.tsx:124`). 이 정책을 유지한다면 위치 전달 영역에서 `닫으면 입력 내용이 지워져요`를 함께 보여 민서가 필요한 내용을 먼저 복사할 수 있게 한다. 실제 통화 성공·신고 접수는 앱에서 확인할 수 없다는 현재 표현을 유지한다.

## 한 장면으로 묶은 개선안

민서가 초록 지도를 열면 조회 기준을 확인한다. GPS가 안 되면 숙소 검색으로, 검색이 늦으면 취소하거나 지도에서 직접 고르는 행동으로 이어진다. 병원 후보를 확보했다면 상세 실패 때문에 전화번호가 사라지지 않는다. 후보가 비어 있으면 같은 검색을 반복시키지 않고 위치 변경으로 이어 준다. 어느 단계에서든 헤더의 도움을 열어 직접 연락하고, 닫으면 원래 보던 화면과 조작 위치로 돌아온다.

완료 기준은 이 흐름 하나로 검증한다. **GPS 거절 + 장소 검색 지연 + 병원 상세 전체 실패**를 순서대로 주입해도 사용자가 현재 조회 기준을 알고, 대기에서 빠져나오고, 이미 검증된 연락처를 사용할 수 있어야 한다. 별도로 **행정구역 경계의 빈 결과**에서 조회 위치 변경까지 한 번의 명시적인 행동으로 갈 수 있어야 한다. 모바일 가독성·누르기 편함·실제 센서 동작은 부모의 브라우저/실기기 검증이 추가로 필요하며, 이 문서는 그것을 통과했다고 주장하지 않는다.
