# 1라운드 · 역발상파 — 더 많이 보여 주는 것이 더 빨리 돕는가

초록색 커스텀 지도는 유지한다. 다음 개선의 목표는 시설 수와 기능 수를 늘리는 것이 아니라, 필요한 시설을 고르고 연락하기까지의 불필요한 판단을 줄이는 것이다. 현재 구현은 자료의 한계를 여러 곳에 설명하고 있지만, 그 설명과 실제 행동 버튼 사이에 간격이 있다.

점검 범위: 2026-10-13 `D:/tourSafe` 소스 직접 열람, 지도 그룹화 순수 함수 실행 1회. 브라우저·실기기 흔들기·외부 전화·실제 제공기관 지연 실험은 실행하지 않았다. 아래 재현 절차는 소스에서 확인한 분기를 검증하기 위한 절차이며, 실제 사용자 테스트 결과가 아니다. 앱 코드·설정·데이터는 변경하지 않았다.

## 사실 1 · P2 · 겹침을 해결한 숫자 원이 필요한 시설의 종류도 함께 숨긴다

- **확인한 사실:** 최초 기본값은 CCTV·경찰·의료 모두 켜짐이다. `groupMapPins`는 시설 종류와 무관하게 화면상 56px 미만의 지점을 같은 그룹으로 묶는다. 2개 이상인 그룹은 아이콘 대신 숫자만 그리며, 좌표가 다르고 확대 한도 전이면 클릭 시 목록이 아닌 확대를 먼저 수행한다. 경찰을 대표 항목으로 고르는 코드는 있으나 혼합 그룹의 화면에는 그 경찰 아이콘을 그리지 않는다. 종류 정보는 `aria-label`에 있고 시각적으로는 숫자에 담기지 않는다.
- **근거:** `frontend/src/utils/mapLayers.ts:8`, `:53`, `:57`; `frontend/src/components/TourSafeMapPanel.tsx:118`, `:125`, `:130`, `:138`.
- **실행한 확인:** 실제 `groupMapPins`에 20px 떨어진 CCTV와 경찰 표본을 전달한 결과는 `[["CCTV","POLICE"]]`였고, 확대 가능성은 `true`였다. 실제 지도에서 어느 시설이 묶이는지까지 확인한 결과는 아니다.
- **UI 재현 절차(미실행):** 두 종류가 가까이 있는 지역에서 기본 레이어로 지도를 연다 → 숫자 원을 보고 경찰 위치를 식별한다 → 숫자를 누른 뒤 확대되고 다시 선택해야 하는지 확인한다.
- **영향 추정:** 경찰이 필요할 때 사용자가 숫자 크기로 후보를 고르거나 반복 확대를 해야 할 수 있다. CCTV 설치자료의 수가 사람에게 도움받을 곳을 찾는 선택에 끼어드는 구조다. 목록 우회 경로가 있으므로 시설이 완전히 접근 불가능하다는 뜻은 아니다.
- **최소 개선:** 겹침 방지와 숫자 원은 유지하되, 혼합 그룹에 경찰·의료 포함 여부를 시각적으로 표시한다. 또는 사용자가 시설 종류에 집중하는 모드에서는 그 종류의 후보 목록을 한 번에 열게 한다. 완료 기준은 “경찰을 찾는 사람이 CCTV 숫자를 해석하지 않고 경찰 후보를 선택할 수 있음”이다.

## 사실 2 · P2 · 이동 버튼은 즉시 보이고, 이동 전에 판단할 제약은 접혀 있다

- **확인한 사실:** 지도에서 시설을 고르면 이름·직선거리 다음에 전화/길찾기를 렌더링한다. 병원의 오늘 등록시간·현재 접수 확인, 응급기관 수용 가능 여부, 화장실 개방시간·현재 이용 가능 여부 안내는 모두 기본적으로 닫힌 `주소·상세 정보` 안에 있다. 전화번호가 없더라도 길찾기는 표시한다. 주소 변환 화장실의 위치 오차 경고는 접힘 밖에 있어 이 부분은 잘 처리되어 있다.
- **근거:** `frontend/src/components/LivePlacesMap.tsx:138`, `:140`, `:141`, `:142`, `:143`, `:145`. 병원 전용 화면은 `frontend/src/components/HospitalFinder.tsx`의 `HospitalCard`에서 전화 확인 문구를 펼쳐 보여 주므로, 동일 시설의 접근 경로에 따라 정보 우선순위가 다르다.
- **재현 절차(미실행):** 의료 또는 화장실 핀 선택 → 상세를 펼치지 않고 길찾기 버튼까지 읽기 → 상세를 펼쳐서야 운영시간/접수/수용 한계가 나오는지 확인한다.
- **영향 추정:** 방문 가능성을 판단하기 전에 이동을 시작할 수 있다. 특히 전화번호 없는 시설에서는 즉시 행동이 사실상 길찾기 하나로 좁아진다. 실제 오방문이 발생했다고 단정하지 않는다.
- **최소 개선:** 길찾기 위에 해당 종류에 맞는 한 줄을 항상 보인다. 예: `현재 접수·수용 여부 미확인 · 방문 전 전화 확인`, `등록 개방시간 09:00–18:00 · 현재 이용 여부 미확인`. 정보가 없으면 그 사실을 적는다. 이미 제공하는 내용을 앞으로 옮기는 변경으로 충분하다.

## 사실 3 · P2 · 부가 정보인 날씨가 도움 시설 표시의 완료 조건이다

- **확인한 사실:** `/api/map-facilities`는 공공시설·응급의료·경찰·날씨를 하나의 `Promise.all`로 기다린 뒤 응답한다. 날씨는 관측 조회 뒤 예보를 순차 조회하며, 각 외부 조회의 timeout은 9초다. 클라이언트는 재조회 시 시설 데이터를 즉시 `null`로 지우고 전체 JSON이 도착해야 새 데이터를 넣는다. 날씨는 지도 설정 안에 표시되는 부가 정보다. 별도 API로 읽는 병원 목록은 이 결합과 구분해야 한다.
- **근거:** `backend/src/services/mapFacilities.ts:14`, `:21`, `:37`; `backend/src/adapters/weatherApi.ts:35`, `:80`; `backend/src/utils/http.ts:36`; `frontend/src/hooks/useMapFacilities.ts:12`, `:15`; `frontend/src/components/LivePlacesMap.tsx:124`.
- **재현 절차(미실행):** 날씨 캐시가 없는 요청에서 다른 시설 응답은 즉시 반환하고 날씨 어댑터만 지연시키는 테스트 더블을 사용한다 → 시설 응답이 날씨 완료 전 도착하지 않는지 확인한다. 실제 제공기관 장애나 현재 지연 시간은 측정하지 않았다.
- **영향 추정:** 경찰·화장실·CCTV 자료가 준비됐어도 날씨를 기다려야 한다. 날씨 새로 조회가 이미 보던 시설을 잠시 지우는 것도 긴급 도움 목적과 맞지 않는다. 항상 9초 또는 18초 느리다는 주장은 아니다.
- **최소 개선:** 날씨를 별도 요청으로 분리하고 시설 응답은 시설 준비 여부로 완료한다. 같은 좌표의 수동 새로고침에서는 이전 시설을 `이전 조회 결과`라고 명시해 유지한다. 위치를 바꾼 경우에는 이전 위치 시설을 섞지 않는다.

## 사실 4 · P2 · 저장 수가 늘어도 저장한 장소에 직접 돌아갈 수는 없다

- **확인한 사실:** 저장소에는 장소 ID만 남는다. 저장 화면은 저장한 ID를 조회하는 별도 목록이 아니라 현재 추천 응답을 저장 ID로 필터링한다. UI도 `저장했던 지역이나 반경으로 다시 찾아보세요`라고 안내한다. 이전 검색 복구는 메모리의 한 단계 참조이므로 새로고침을 넘어서 저장 장소의 이름·위치를 복원하지 않는다.
- **근거:** `frontend/src/utils/savedPlaces.ts:10`, `:36`, `:114`; `frontend/src/ExploreApp.tsx:57`, `:68`, `:72`, `:466`. 처음 여행지 화면의 기본 검색은 같은 파일 `:42`, `:46`에서 `DEFAULT_REGION`이다.
- **재현 절차(미실행):** 기본 지역 밖 관광지를 검색해 저장 → 새로고침 후 저장 화면 열기 → 총 저장 개수는 남지만 현재 검색에 그 장소가 없으면 카드·직접 열기 경로가 나오지 않는지 확인한다.
- **영향 추정:** “나중에 다시 찾으려고 저장”했는데 사용자가 원래 지역·반경을 기억해 다시 검색해야 한다. 저장 개수는 기능 성공을 암시하지만, 여행 중 재접근이라는 핵심 작업을 완료하지 못한다. ID가 삭제되었다는 주장은 아니다.
- **최소 개선:** 저장 시 ID와 이름·좌표·주소의 최소 스냅샷을 함께 보관해 검색 범위와 독립된 저장 목록을 제공한다. 다시 열 때 최신 정보를 조회하고, 조회 실패 시에도 저장 시점 자료임을 밝혀 이름·주소·저장 해제에 접근하게 한다. 영업 정보를 최신으로 가장하지 않는다.

## 사실 5 · P2 · 흔들기 켜짐은 다른 화면이 떠 있으면 동작하지 않는 켜짐이다

- **확인한 사실:** 흔들기 안내는 `앱 화면을 보고 있을 때, 흔들면 이 화면을 열어요`라고 말한다. 그러나 감지기는 `document.querySelector('dialog[open]')`가 참이면 샘플을 버리고 반환한다. 시설 목록·지도 설정·병원·장소 상세처럼 일반 앱 대화창이 하나라도 열리면 감지가 중단되며, `enabled` 값은 그대로다. 대화창 헤더에는 수동 도움 버튼이 있어 대체 접근은 제공된다.
- **근거:** `frontend/src/components/EmergencyHelp.tsx:116`; `frontend/src/hooks/useShake.ts:25`, `:33`; `frontend/src/components/Modal.tsx:57`.
- **재현 절차(실기기 미실행):** 센서 지원 기기에서 흔들기 켜기 → 도움 닫기 → 시설 목록이나 병원 창 열기 → 같은 흔들기 제스처 수행. 코드상 열려 있는 일반 대화창 때문에 콜백에 도달하지 않는다. 실제 센서 인식률은 평가하지 않았다.
- **영향 추정:** 여행지를 읽거나 병원을 고르는 중에도 앱을 보고 있으므로 안내와 사용자의 기대가 어긋날 수 있다. 현재 도움 화면의 중복 호출 방지와 모든 일반 대화창에서 기능 중단을 구분할 필요가 있다.
- **최소 개선:** 도움 화면 자체가 열렸을 때만 중복 실행을 막고, 일반 대화창에서는 기존 수동 도움 버튼과 같은 경로로 도움을 열도록 한다. 의도적으로 제한을 유지한다면 `목록·상세 창에서는 작동하지 않아요`를 설정 설명과 상태에 명확히 표시한다.

## 정성 제안 2개

1. **첫 판단을 시설 표시 토글에서 필요한 도움 선택으로 바꾼다.** 현재 초록 지도·레이어·클러스터는 유지하되 `경찰 찾기`, `병원에 전화`, `화장실 찾기` 중 선택하면 가까운 후보 3개와 연락/운영 확인을 바로 보여 주는 흐름을 우선 실험한다. CCTV는 설치 사실을 읽는 보조 레이어로 두고 시설 수를 서비스의 성과처럼 강조하지 않는다. 이것은 사용자 실험이 필요한 설계 가설이며 검증된 우월성 주장이 아니다.
2. **위치 한 번 선택의 가치를 화면 사이에 이어 준다.** 지도에서 지역을 바꾼 뒤 `여행지 조건으로 검색`을 누를 때 같은 조회 위치로 넘어가도록 한다. 현재 `LivePlacesMap.tsx:174`의 호출에는 위치가 없고, `App.tsx:71`의 `ExploreApp`에도 전달되지 않아 `ExploreApp.tsx:42`의 독립 기본 위치로 시작한다. 최소한 전환 직후 새 화면의 조회 기준을 명확히 보여 준다. SOS 위치는 실제 기기 위치를 새로 확인하는 현재 원칙을 유지한다.

## 실행 순서와 검증 기준

1. 흔들기 조건과 안내 일치, 카드의 전화/길찾기 앞 제약 표시부터 수정한다. 작은 변경으로 사용자가 행동 직전에 알아야 할 조건을 드러낼 수 있다.
2. 날씨 조회를 분리하고, 저장 장소의 독립 접근을 구현한다. 성공 기준은 날씨 지연 중 시설 사용 가능, 새로고침 후 다른 지역 저장 장소 직접 열기다.
3. 혼합 클러스터를 개선한 뒤 모바일에서 “경찰 후보 한 곳 선택”과 “화장실 운영시간 확인”의 성공률·행동 횟수를 비교한다. 숫자 원을 줄이거나 늘리는 것 자체를 성공 지표로 삼지 않는다.

관찰상 유지할 점: 도움 화면은 위치 허용을 기다리지 않고 112·119 전화 앱을 열게 하며, 자동 신고로 표현하지 않는다. 자료 없음과 시설 없음도 구분하려고 한다. 총체 점검의 쟁점은 이 원칙을 지도 카드·저장·흔들기·로딩 구조까지 일관되게 이어 가는가다.
