# 4강 판정과 결승 진출 답변

점수 순서: 상황 해결 / 추가 사용 편의 / 신뢰성 / 실행 가능성 / 검증 가능성. 각 5점. 상호 공격으로 드러난 약점을 반영한 재평가이며 실제 사용자 점수가 아니다.

## S1 역발상파 승
역발상파 4/5/5/4/5 = 23, 숫자파 4/4/5/5/4 = 22.
역발상파 공격: 기존 지도보다 빠르다는 결과만으로 단순 안내문보다 더 복잡한 서비스를 만들 이유를 알 수 없다.
숫자파 공격: 숙소 QR 유입도 협조 확보도 미입증이며 숙소 위치는 이동 중 여행객의 위치가 아니다.
판정: 저비용 대체재와 처음 접근하는 경로를 함께 다룬 역발상파가 근소 우세. 숙소 QR 가설이 성립하는지는 별도 검증해야 한다.
흡수하는 요소 딱 하나: 숫자파의 '어디에 연락하고 무엇을 확인할지 정확히 정했는가'를 완료 조건으로 삼는다.

### 결승 A — 역발상파 수정 답변
지금 투어세이프를 별도 지도 앱으로 계속 열 이유는 입증되지 않았다. 주변 검색·시간 정보·길찾기는 기존 지도에 있고, 흔들기 신고 등은 서울시 안심이에도 있다. 우리 자료도 병원 접수 가능 여부나 CCTV 작동을 알려주지는 않는다. 그래도 흩어진 정보의 출처와 미확인 상태를 정리해 다음 행동을 쉽게 만들 수 있다는 가설은 시험할 만하다.

첫 장면은 해운대 숙소에 머무는 보호자가 아이의 진료를 문의할 곳을 찾는 순간이다. 숙소 안내에서 설치 없이 열리는 작은 웹 화면에 숙소 기준 위치·진료과·등록시간·전화·자료 기준일을 모으고, 접수 여부는 미확인으로 표시한다. 직접 확인 후 기존 지도 길찾기를 사용한다. 녹색 지도는 위치를 이해하는 화면으로 유지할 수 있다. 숙소 기준을 실제 현재 위치처럼 표시하지 않으며, 이 제안은 숙소 안에서의 장면으로 한정한다. 숙소 제휴와 해당 안내 흐름은 아직 없다.

평소 지도, 전화번호와 확인사항을 적은 단순 안내문, 투어세이프를 비교하자. 완료는 연락처를 찾는 것과 어디에 연락해 무엇을 확인할지 정확히 이해하는 것 모두를 포함한다. 오해 없이 정확히 끝내는가를 우선하고 시간·재검색을 함께 본다. 투어세이프 표시를 접수 보장으로 이해한 사례가 있으면 먼저 수정한다. 속도 실험 통과만으로 독립 앱 수요를 선언하지 않는다.

그다음 실제 필요가 발생했을 때 링크를 스스로 찾고 사용하는지 본다. 숙소 한 곳에 안내를 제공할 협조가 성립하는지도 사전 확인해야 하며, 성립하지 않으면 QR 유입 가설은 중단한다. 단순 안내문과 이득이 같으면 같은 목적을 더 단순한 형식으로 제공한다. 기존 지도보다 불편하거나 필요할 때 실제로 쓰이지 않으면 이 장면의 가설을 기각한다. 앱 설치와 대규모 기능 확장은 이 증거를 본 뒤 결정한다.

## S2 전문가파 승 (동점, 구체성 판정)
고객 시점파 5/3/5/5/4 = 22, 전문가파 5/5/5/4/3 = 22.
고객 시점파 공격: 사용 효과가 화면에서 오는지 운영자의 수동 갱신·확인에서 오는지 분리되지 않는다.
전문가파 공격: 보호자가 필요 순간에 발견할 경로가 없고, 화면을 제공한 실험은 최초 선택과 유지비용을 검증하지 못한다.
판정: 고객 시점파는 읽기·행동 화면의 구체성이 강하다. 동점에서 전문가파의 고정된 제공 장소, 반복 문의를 받는 담당자, 기록할 운영 비용이 더 구체적이므로 결승 진출. 숙소 문의량은 여전히 가설이며 수작업 부담을 정량화해야 한다.
흡수하는 요소 딱 하나: 고객 시점파의 '접수 여부는 전화 확인 필요'를 등록시간 바로 옆에 배치한다는 표현 설계.

### 결승 B — 전문가파 수정 답변
현재 투어세이프의 차별성은 미입증이다. 한 관광권의 숙소 야간 직원이 투숙객의 병원 문의를 받는 장면에서, 위치와 확인 상태가 정리된 도움 연결 도구를 시험하자. 여러 손님의 비슷한 질문을 받는 직원에게 반복 사용 기회가 있을 수 있다는 가설이다. 문의량과 제휴가 확보된 것은 아니다.

숙소 위치를 기준으로 기관의 등록 진료시간·전화·외부 길찾기를 정리하고, 시간 바로 옆에 '접수 여부는 전화 확인 필요'를 표시한다. 사람이 전화로 확인한 정보는 시각과 질문·답변 범위를 남기고 다음 손님의 접수 가능 상태로 재사용하지 않는다. 응급상황을 이 문의표로 지연시키지 않는다. 현재 위치와 조회 지역의 불일치, 누락 연락처와 오래된 자료가 있는 제품을 완성된 운영 도구라고 주장하지 않는다.

앱 확장 전 한 관광권 숙소 3곳·2주 수동 시험을 제안한다. 기존 지도와 사용 순서를 교차해 비교하며, 문의 해결 시간·잘못 연결된 연락처·다음 문의에서의 자발적 재사용·정보 갱신 시간을 기록한다. 화면 효과와 운영자가 대신 확인한 효과를 구분해야 한다. 전체 절약 시간이 갱신 부담을 넘는지 보고 최소 관찰량과 허용 유지 시간을 시작 전에 정한다. 문의가 적으면 관찰 조건을 재검토한다. 문의가 있어도 기존 지도만 쓰거나 운영자가 매번 대신 전화해야 한다면 확장하지 않는다.

차별성이 생긴다면 공공시설 핀의 수보다 좁은 지역의 오류를 고치고 확인 상태를 관리하는 운영 능력에서 나올 수 있다. 단순 문의표로 충분하면 그 형태에 머물고, 재사용과 유지 가능성이 입증될 때 제품화한다. 소규모 시험 통과가 전국 서비스 수요나 사업성을 증명하지는 않는다.
