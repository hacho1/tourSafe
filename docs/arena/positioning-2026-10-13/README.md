# 투어세이프를 다시 켤 이유가 있는가 — 아레나 결과

2026-10-13 · 독립 도전자 8명 · 8강 4경기, 4강 2경기, 결승 1경기. 도전자들은 같은 구현 근거와 공식 경쟁 서비스 자료를 받고 서로 다른 전략으로 답했다. 각 경기에서 양쪽 에이전트가 서로 공격했고, 주 에이전트가 기준별 심사와 패자 요소 한 가지를 흡수한 수정을 수행했다. 아래 점수는 AI의 정성 판단이며 시장 조사 결과가 아니다.

## 서버 재시작

TourSafe 개발 서버 프로세스임을 확인한 뒤 기존 프로세스 트리를 종료하고 D:/tourSafe에서 `npm run dev`로 웹과 API를 다시 실행했다.

- 웹: http://127.0.0.1:5173/#map — HTTP 200, 새 PID 18572.
- API: 8787, 새 PID 29816. 웹 프록시를 통한 `/api/health` 응답 `ok: true`, `mode: LIVE`, 지도·장소 검색 설정 확인.
- `/api/map-facilities` 재조회: 공공파일·응급의료·경찰·날씨 상태 모두 OK. 이번 확인 좌표 37.5445, 127.0557에서 CCTV 40, 응급의료 3, 경찰 3개 시설 반환. 이는 실제 사용자 위치나 전국 시설 수가 아니다.
- 이번 작업에서 앱 기능·설정·인증키는 변경하지 않았다. 서버 재시작과 검토 문서만 작성했다. 기능 변경이 없어 전체 빌드/테스트를 재실행하지 않고 HTTP와 실제 조회로 확인했다.

## 🏆 우승 답 — 역발상파

**지금 투어세이프는 기존 지도를 두고 별도로 계속 쓸 이유가 아직 약하다. 다만 낯선 여행지에서 도움받을 곳을 찾고, 무엇을 확인해 어디로 연락할지 정하는 수고를 줄인다면 쓸 이유가 생길 수 있다.** 이것은 사용자 행동으로 검증할 제품 가설이며 현재 확보한 경쟁 우위가 아니다.

익숙한 정보도 특정 상황에서 더 적은 수고로 쓰게 정리하면 가치가 있을 수 있다. 현재의 간결한 녹색 지도는 유지할 장점이다. 지도 색상, CCTV 핀의 수, 흔들기 같은 개별 기능이 그 자체로 재사용을 보장하지는 않는다.

첫 시험 장면으로 '해운대 숙소에서 아이의 진료를 문의할 곳을 찾는 보호자'를 제안한다. 숙소 안내에서 설치 없이 열리는 웹 화면에 조회 위치, 해당 진료과가 등록된 후보, 등록시간, 전화번호, 출처·자료 기준일을 정리한다. 접수 여부가 확인되지 않았음을 분명히 표시하고, 전화 확인과 기존 지도 길찾기로 연결한다. 긴급한 상황의 응급 여부를 판정하거나 이 과정을 먼저 거치게 만드는 서비스는 제안하지 않는다. 숙소 협조와 이 흐름은 아직 확보·완성된 기능이 아니다.

**검증할 약속: '낯선 여행지에서 도움받을 곳과 다음 행동을 덜 헤매고 정한다.'** 병원 탐색은 첫 시험 과제이지 투어세이프의 모든 방향을 병원 앱으로 확정한다는 뜻은 아니다. 다른 도움 상황으로 넓힐지는 이득을 확인한 뒤 판단한다.

작은 시안으로 평소 지도, 전화번호·확인사항을 적은 안내문, 투어세이프를 비교한다. E-GEN 같은 의료 정보 서비스도 현재 흐름을 직접 확인한 뒤 비교에 포함한다. 완료는 '전화번호를 찾았다'에 그치지 않고 어디에 연락해 무엇을 확인할지 정확히 이해했음을 포함한다. 잘못된 확신·재검색·소요시간을 함께 보고, 등록시간을 접수 보장으로 오해한다면 먼저 화면을 수정한다. 임의의 속도 문턱 하나로 전체 효용을 판정하지 않는다.

모의 과제를 잘 풀었다고 실제 사용 이유가 입증되지는 않는다. 이후 필요가 실제 생긴 상황에서 안내를 스스로 발견하고 다시 선택하는지 관찰한다. 필요가 없던 여행은 실패로 세지 않는다. 숙소 안의 상황을 숙소 기준으로 안내하며, 이동 중 사용자가 있는 위치와 혼동하지 않도록 한다. 협조 숙소에서 접근 경로 자체가 성립하지 않으면 QR 배포 가설은 중단한다.

마지막으로 **정보 갱신에 드는 시간도 기록한다.** 이것이 결승에서 전문가파로부터 흡수한 한 요소다. 이용자가 덜 검색하게 되어도 운영자가 계속 대신 검색·확인해야만 유지된다면 작은 팀이 확장하기 어렵다. 단순 안내문이나 기존 서비스 링크와 효과가 같으면 더 단순한 형식으로 제공한다. 정확한 완료·자발적 선택·감당 가능한 유지 비용에서 추가 이득이 관찰될 때 기능을 확대한다.

## 왜 이겼나

1. 추가 사용 편의: 사용자가 어디서 이 서비스를 발견할지까지 검증 대상으로 삼았다.
2. 실행·검증 가능성: 앱 확장 전에 단순 안내문과 작은 웹 시안으로 개발 필요성을 확인할 수 있다.
3. 신뢰성: 안전·접수 가능을 단정하지 않고, 사용자 정확성과 자료 유지 비용을 함께 본다.

## 아깝게 진 답 — 전문가파

**숙소 야간 직원이 손님 문의를 처리하는 도구부터 시험하자.** 여행객 한 명에게는 드문 일이 직원에게 반복될 수 있다는 가설이다. 좁은 지역의 연락처 오류, 확인 시각과 범위를 관리하면 공공데이터를 모으는 것 이상의 운영 가치가 생길 수 있다.

장점은 반복 사용과 유지 비용을 같은 현장에서 볼 수 있다는 것이다. 약점은 숙소의 실제 문의 빈도와 협조가 확인되지 않았고, 사람이 대신 확인해 준 효과와 소프트웨어의 효과를 분리해야 한다는 것이다. 문의표 한 장으로 충분하면 그 형태에 머물러야 한다. 소비자용 제품과 다른 고객·운영 구조이므로 현장 수요를 확인하고 선택할 대안이다.

## 디자인과 다음 단계 제안

- 간결한 녹색 지도는 유지한다. 도움을 요청할 때 필요한 소수 후보와 다음 행동이 먼저 읽히는지 시험한다.
- 현재 위치·선택한 위치·조회 기준점을 일치시키는 흐름이 우선이다. 현재 주요 지도와 별도 GPS 탐색 흐름이 나뉘어 있다.
- 병원 등록시간을 현재 접수 가능으로, CCTV 설치 밀도를 실제 안전으로 해석하게 만드는 점수·색상은 근거가 없다. 실제 정보의 의미를 정확히 전달한다.
- 다음 코딩 단계로 들어가기 전에 한 장면의 화면 시안과 비교 과제를 준비할 것을 권고한다. AI·워치·자동 신고·안전 경로 등을 추가할지는 이 검증과 각각 필요한 데이터·운영 조건을 확인한 뒤 결정한다.
- 숙소 배포·직원 도구·새 행동 화면은 이번에 구현하지 않았다. 기존 녹색 지도와 연결 API는 유지되어 있다.
