🏆 우승안: 전문가파 — 재현된 오류를 먼저 고치고, 위치·저장 정보의 의미를 정한 뒤 오프라인으로 확장한다.

전체 판정
현재 구현은 DEMO 체험과 기능 확인이 가능한 상태다. 테스트 64개와 빌드는 통과했다. 다만 이번 검토에서 자동 테스트가 다루지 않은 위치 선택 충돌, 저장 실패 표시, 화면 왕복의 상태 초기화가 재현됐다. 4단계를 붙이기 전에 이 오류와 긴급 도움 진입의 불일치를 정리하는 것이 좋다.
사용자가 느낀 어지러움에는 실제 구조적 원인이 있다. 기능마다 큰 진입 영역이 쌓이고, 화면에 따라 하단 메뉴의 뜻이 바뀌며, 검색 조건이 유지되지 않는다. 색상을 전면 교체하기보다 공통 이동 규칙과 정보 우선순위를 먼저 고치는 안을 권한다.
이번 작업은 점검·보고서·캡처만 수행했다. 제품 소스 수정이나 4단계 구현·외부 배포는 하지 않았다.

방법
arena 스킬에 따라 독립 도전자 8명(audit_arena_1~8)을 동시 3명 이내로 나누어 실행했다. 같은 brief와 기준을 주고 각자 다른 전략을 배정했다. 첫 제출까지 다른 답안은 공유하지 않았다. 주 에이전트는 실제 화면, 소스, API 응답, 테스트·빌드를 확인했다.
8강·4강의 상호 비판은 제출안을 바탕으로 심사자가 구성했다. 결승에서는 정석파1와 전문가파7에게 실제 상대안과 재현 결과를 전달해 직접 반박·흡수안을 받았다. 아래 점수는 내부 답안 비교점수이며 앱 품질점수, 사용자 조사, 실기기 인증이 아니다.

먼저 고칠 항목

1. 위치를 수동 선택한 뒤에도 이전 GPS 응답이 덮어씀 [현재 브라우저에서 모의 재현 / P2 기능 오류]
재현: 여행지→출발 위치 선택→현재 위치 사용. 실제 GPS 대신 30초 뒤 공개된 기준점 좌표를 반환하는 일시 대체 함수를 사용했다. 기다리는 중 부산 해운대를 선택하면 처음에는 부산으로 표시되지만, 늦은 응답 후 '내 현재 위치 / 위치 정확도 약20m'로 바뀌었다. 실제 위치 권한·GPS는 사용하지 않았다.
근거: frontend/src/components/SearchPanel.tsx:47,57,158,162. 닫기나 수동 선택 시 요청을 무효화하지 않고 성공 콜백이 onRegion을 호출한다.
수정 방향: 닫기·수동 선택·새 요청에서 이전 요청 세대를 무효화. 유효한 최신 요청만 반영. 새 SOS와 Nearby에 있는 통제 방식을 기존 검색에도 적용.
통과조건: GPS 대기→부산 수동 선택→늦은 성공/실패에도 부산 유지. 닫기·재진입도 동일.
증거: location-before.jpg, location-after.jpg. 검증 후 새로고침으로 대체 함수 제거.

2. 영구 저장에 실패해도 하트가 저장 성공처럼 바뀜 [현재 브라우저에서 모의 재현 / P2 기능 오류]
재현: toursafe-saved 쓰기만 QuotaExceededError를 던지도록 일시 대체. 숲속 자연생태공원의 하트를 누르면 aria-pressed=false→true, '저장 취소'로 바뀌었다. 실패 안내 없이 새로 열면 false로 돌아왔다.
근거: frontend/src/hooks/useSavedPlaces.ts:20~25에서 저장 오류를 삼키고 next를 반환; frontend/src/components/SpotCard.tsx:64가 이를 표시.
수정 방향: 영구 저장 성공, 이번 실행에서만 유지, 실패 상태를 구분. 사용자가 재시도하거나 저장 공간 문제를 이해할 수 있게 안내.
통과조건: 저장소 오류에서 영구 저장 성공으로 표시하지 않음. 재실행 후 상태와 안내가 일치함.
증거: save-failure.jpg. 실제 저장 데이터 쓰기는 일어나지 않았고 새로고침으로 대체 함수 제거.

3. 화면을 왕복하면 검색 조건이 초기화됨 [현재 브라우저 재현 / P2 사용성 문제]
재현: 여행지에서 반경1km 검색→안심 지도→여행지. 반경이3km로 돌아온다. URL도 별도 화면 경로로 갱신되지 않는다.
근거: frontend/src/App.tsx:23~26 조건부 렌더링, frontend/src/ExploreApp.tsx:42~51 내부 초기값. 지역·정렬·보기·필터도 같은 수명에 묶인다(나머지 조건은 코드 판단).
수정 방향: 공통 탐색 상태를 유지하고 뒤로가기·화면 복귀 규칙을 정한다. 상세 복귀의 초점과 스크롤도 함께 확인.
통과조건: 지도 왕복 후 지역·반경·정렬·보기 유지, 사용자가 의도한 초기화에서만 초기화.

4. 긴급 도움 경로가 화면마다 다름 [현재 화면+코드 확인 / P2 흐름 개선]
기존 장소 상세 하단은 frontend/src/pages/SpotDetail.tsx:491의 tel:119 링크로 바로 이동한다. 새 SOS는 번호 선택 뒤 실제 번호 안내와 전화 앱 버튼을 보여준다. DEMO 장소 상세에도 직접119 링크가 남아 있다.
직접 tel 링크는 사용자가 누르는 전화 링크이며 자동 발신·자동 신고 오류라는 뜻은 아니다. 실제 통화 시작 여부는 OS/전화 앱에 따르며 이번 점검에서는 링크를 실행하지 않았다. 다만 새 SOS와 방식이 다르고 상세 지도탭의 가상 시설 전화 미제공 문구도 구분을 더 명확히 할 필요가 있다.
또한 일반 모달은 Modal.tsx:17 showModal()로 배경 헤더 접근을 막는다. 주변 장소→병원 상태에서는 공통 SOS에 가기 위해 병원과 주변 창을 차례로 닫아야 한다. 현재 접근성 트리와 병원 캡처에도 내부 SOS 진입점이 없다.
수정 방향: 상세·병원·주변 화면에서도 의도된 동일 SOS 흐름으로 이동하고, 취소하면 원래 맥락으로 복귀. 모달 중첩 시 스크롤 잠금·초점 복구도 함께 설계.
통과조건: 주요 화면에서 긴급 도움 진입·취소가 일관됨. 전화 실행 없이 화면과 링크만 검사.
증거: legacy-detail-119.jpg, hospitals.jpg.

홈: 안심 지도 / 여행지 / 주변 장소 / 저장.
여행지: 안심 지도 / 둘러보기 / 저장한 곳 / 이용 안내.
같은 세 번째·네 번째 위치의 역할이 달라진다. SafetyMap.tsx:105, ExploreApp.tsx:501. 이름·순서·목적지를 통일하고 안내는 보조 위치로 옮기는 것이 좋다.

6. 저장 목록의 범위와 오프라인 자료를 구분할 것 [현재 재현 / 설계 한계]
1.6km 예시 장소를 저장한 다음 검색 반경을1km로 바꾸고 저장한 곳을 열면0개가 나온다. 실제 저장 ID가 삭제된 것이 아니라 현재 추천 결과와 저장 ID의 교집합만 보여주는 동작이다(ExploreApp.tsx:62~65). 화면에도 '현재 검색 범위의 저장한 장소'라고 안내한다.
따라서 이를 데이터 삭제 버그로 부르면 부정확하다. 하지만 일반 사용자는 저장한 장소 전체를 기대할 수 있다. 범위 밖 항목을 다시 찾는 경로, 전체 저장 목록, 북마크와 다운로드 자료의 차이를 4단계 설계에서 정해야 한다. 독립 저장 목록을 완성해야만 오프라인 개발을 시작할 수 있다는 절대 조건은 아니다.
재현에 사용한 예시 하트는 원래 미저장 상태로 복원했다. 증거: saved-missing.jpg.

7. 화면 밀도와 점수의 표현을 통일할 것 [실측+설계 판단]
390×844 현재 홈 문서높이1927px, 지도 시작y502px, 경로 선택y1040px. 병원 첫 카드y약556px, 펼침 영역9개(4개 병원). 이전 검토와 같은 밀도다.
주변 장소에서는 방문 조건 계산을 접어 두지만 여행지 카드에서는97/100과정보100%가 크게 보인다. 이는 계산 로직이 있는 가상 자료의 예시이며 안전확률이나 정보 정확도는 아니다. 예시 고지가 없다는 지적은 기각한다. 고지는 실제로 존재한다. 표시된 숫자와 효용 문구가 더 강하게 읽힐 가능성은 사용성 검증 대상으로 남는다.
수정 방향: 공통 메뉴/상태를 먼저 정리한 뒤 큰 진입 카드·소개를 줄이고, 병원은 선택한 요일 등록시간을 먼저 보여준다. 출처는 보조 펼침으로 묶되 DEMO·지역 기준·미확인 표시는 유지.

추가 확인할 항목(현재 재현과 구분)
- Nearby LIVE 위치는 획득 시각 없이 부모에 유지되면서 '현재 위치 · GPS'라고 표시된다. 이동 후 재진입에서는 '마지막 확인 위치'와 시각/재확인이 적절하다. 현재 DEMO에서는 GPS 진입이 차단되어 있어 이번 실기기 재현은 없음. SafetyMap.tsx:25, NearbyScore.tsx:169.
- SearchPanel의 위치 버튼은 이후 검색 시 서버로 좌표를 보낸다는 목적 안내가 Nearby보다 약하다. 실제 유출 증거가 아니라 안내 일관성 개선. services/api.ts:25, NearbyScore.tsx:262.
- 병원 조회 실패 원인을 services/hospitals.ts:8에서 일반 오류로 바꾸고 HospitalFinder.tsx:48에서 연결 확인 안내로 축약한다. 승인·기관 실패와 네트워크를 구분할 수 있게 보완. 이번에는 실제 승인키 오류를 재현하지 않음.
- HospitalFinder.tsx:76 재조회는 선택 진료과를 전체로 초기화한다. 유지 가능한 선택은 유지하고 선택 항목이 사라진 경우에만 설명하는 방향 검토.
- 병원→주변 결과 복귀의 초점 복원은 결과 재조회보다 먼저 실행될 수 있다(SafetyMap.tsx:45). 느린 응답에 대한 키보드 복귀 재현이 후속 검증 항목.

잘 된 부분 / 유지할 것
- 주변 정보와 병원에 DEMO·미확인을 표시한다. 병원 결측 시간을 휴진으로 단정하지 않고 등록시간/익일 종료와 지역 기준 직선거리를 구분한다.
- 병원 DEMO에서 실제 병원 전화/지도 연결을 제공하지 않는다. 실제 SOS 번호는 별도 기능으로 명시한다.
- 새 SOS 위치는 직접 요청, 일회성,2분 만료, 취소 뒤 늦은 응답 차단, 서버·영구저장 미전송으로 구성되어 있다. 실제 GPS는 시험하지 않았고 유틸 테스트와 코드로 확인.
- API에 no-store가 있으며 SW가 /api 응답을 저장하지 않는다. 최신 응답 실패를 자동으로 DEMO로 바꾸는 구조는 차단되어 있다.
- 현재64개 테스트와 빌드 통과. 테스트명 hospital-ui는 React 실화면 전체 시험이 아니라 유틸 시험임을 구분한다.

4단계 진행 순서
1. 기존 검색 GPS 요청 무효화와 저장 실패 표시를 먼저 수정하고 모의 회귀 검증.
2. 공통 SOS 진입, 하단 메뉴, 화면 왕복 상태를 정리. 큰 시각 개편은 필요하지 않음.
3. 오프라인 저장 자료의 계약: DEMO/LIVE, 자료 출처, 기준 지역/좌표의 의미, 원자료 시각, 저장 시각, 유효성·재확인 필요 상태, 삭제 규칙. SOS의 민감한 현재 위치는 자동 저장 대상에서 제외.
4. 운영 빌드에서 온라인 준비→통신 차단→앱 재실행→자료 읽기→만료·오류 표시→삭제를 검증. 개발 서버는 main.tsx:10에 따라 SW가 등록되지 않으므로 지금의 개발 화면만으로 오프라인 검증 완료를 주장하지 않음.
5. LIVE 기관 응답, 실기기 위치/센서/전화 앱은 별도 검증. 이 검증이 끝나지 않았다고 DEMO 기반 4단계 개발까지 막을 필요는 없지만 실제 여행용 준비 완료라고 표현해서는 안 됨.

독립 답안 요약
1 정석파: SOS 경로·GPS 요청·탐색 상태를 표준화. 전체 여정 연결에 강함.
2 역발상파: 저장의 의미와 예시 지도 효용 표현을 먼저 정리. 기능 확대의 약속을 짚음.
3 숫자파: 테스트 범위·오류 분류·저장 실패의 근거를 분리. 미검증 영역을 과장하지 않음.
4 스토리파: 장소→병원→SOS→복귀 장면에서 접근성·조건 유지·초점을 검토.
5 고객 시점파: 긴급 도움, 메뉴 위치, 저장 장소 재발견의 예측 가능성을 강조.
6 극단 간결파: 모달 SOS·공통 메뉴·검색 상태의 세 수정에 집중.
7 전문가파: 위치 응답/획득시각/전송 목적, 현재 결함과 미구현 기능의 구분에 집중.

8강2 숫자3 vs 스토리4
3의 공격: 한 여정에서 보이지 않는 저장 실패와 실제API 검증 한계를 빠뜨린다.
4의 공격: 검증 공백만 강조하면 현재 화면에서 어디를 고칠지 우선순위가 약해진다.

흡수: 저장 실패 시 성공 표시를 하지 않는 수용조건과 시험 범위 구분.

8강3 고객5 vs 간결6
5의 공격: 세 가지 개선만으로 저장 항목을 다시 찾지 못하는 장면은 해결되지 않는다.
6의 공격: 여러 발견을 모두 필수로 두면 단순한 정리 작업이 전면 개편으로 커진다.
판정: 5=9/9/8/8/8=42, 6=8/9/8/8/8=41. 승자5.
흡수: 모달 안 긴급 진입·공통 메뉴·상태 보존부터 작게 적용.

8강4 전문가7 vs 실험8
7의 공격: 아직 만들지 않은 오프라인 읽기를 현재 결함처럼 세면 개발 준비 기준이 과도해진다.
8의 공격: 위치 정확성만 정리해도 저장 실패의 성공 표시와 긴급 접근 단절은 남는다.
판정: 7=9/8/9/9/9=44, 8=8/8/8/8/8=40. 승자7.
흡수: 저장소 쓰기 실패를 모의하고 표시·재진입 상태를 함께 검증.

4강1 정석1' vs 스토리4'
1의 공격: 병원 한 흐름의 초점 복원보다 여러 화면에 걸친 GPS·저장 상태 오류를 먼저 처리해야 한다.
4의 공격: 공통 SOS 통합이 배경 헤더 변경에 그치면 모달 안 접근 문제는 남는다.

4강2 고객5' vs 전문가7'
5의 공격: 기술적 위치 계약만으로 사용자가 기억한 메뉴 자리와 검색 조건을 지킬 수는 없다.
7의 공격: 범위 밖 저장 항목을 데이터 삭제로, 직접 전화 링크를 자동 발신으로 해석하면 결함을 과장한다.
판정: 5'=9/9/8/9/9=44, 7'=9/9/9/9/9=45. 승자7'.
흡수: 메뉴·검색 맥락·저장 재발견을 별도의 사용성 정리 항목으로 명시.

결승 정석1'' vs 전문가7'' (두 에이전트의 실제 상호검토)

7의 공격: 독립 저장목록은 현행 필터 방식의 확장인데 데이터 소실 버그로 취급하면 선행조건이 과도해진다.
양측 모두 재현된 GPS 충돌·저장 실패를 먼저 수정하는 것으로 최종안을 보완했다.
판정: 1''=9/9/9/9/9=45, 7''=10/9/9/9/9=46. 승자7''.
흡수: 상세119·모달 내부를 포함한 공통 긴급 도움 통합을 최종안에 포함.

왜 이겼나
1. 실제 재현된 오류와 사용성 개선, 아직 없는4단계 기능을 구분해 과장하지 않았다.
2. SOS·위치·저장의 정보 의미를 유지하면서 작은 수정 순서를 제시했다.
3. 실제GPS/LIVE 미검증을 인정하되 DEMO 기반 개발 착수까지 불필요하게 막지 않았다.

준우승: 정석파의 '공통 탐색과 긴급 도움을 먼저 통일'하는 안. 메뉴·상태 중심의 다음 구현 계획을 잡기에는 이 안이 더 직관적이다. 최종 권고는 전문가파의 근거 구분 위에 정석파의 화면 연결 개선을 포함한다.
